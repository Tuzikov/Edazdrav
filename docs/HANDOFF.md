## На заметку (грабли, на которые уже наступали)

### Supabase keep-alive — паузился повторно, пинг был слишком редким
Несмотря на воркфлоу `.github/workflows/keep-alive.yml` (добавлен ещё в
августе), проект **снова ушёл в паузу** в сентябре. История запусков
показала: пинг `2026-09-14` получил живой ответ `200` от базы, а
следующий по расписанию (`2026-09-17`, через 3 дня) упал с
`curl: (6) Could not resolve host` — проект был уже полностью выгружен, то
есть заметно раньше формального 7-дневного порога бездействия. Расписание
было `пн и чт` (2 раза в неделю) — судя по всему, недостаточно часто:
документация Supabase формулирует порог расплывчато («обычно достаточно
нескольких запросов к БД **в день** на протяжении недели»), то есть их
реальная эвристика активности жёстче буквальных «7 дней» без запросов.
**Исправлено**: расписание пинга увеличено до раза в 6 часов (`0 */6 * *
*`). Если и это не поможет — единственный по-настоящему надёжный вариант
это платный тариф Supabase (Pro, там паузы по неактивности нет вообще);
пинг любой частоты — это обход, а не гарантия.

**Важно**: разбудить уже приостановленный проект **нельзя** ни через
`supabase` CLI (проверено — там только `list/create/api-keys/delete`, ни
`restore`, ни `resume` нет), ни через какой-либо API — только кнопка
«Restore project»/«Resume» в Supabase Dashboard
(https://supabase.com/dashboard/project/iwqabjqsrqvmqciikzqn), и нажать
её может только сам пользователь (залогиненный человек), не агент.

### Распознавание фото зависало навечно — не было ни одного таймаута в цепочке
30.10, после месяца без использования приложения, пользователь сообщил:
после фотографирования блюда экран "Анализ" висит бесконечно на "идёт
отправка фото", без ошибки.

**Диагностика.** Сначала проверил, не в паузе ли Supabase (это уже было
несколько раз, см. раздел про keep-alive) — нет, `ACTIVE_HEALTHY`, REST
отвечает `200`, воркфлоу `keep-alive.yml` все зелёные последние недели по
расписанию `*/6h`. Проверил сам `recognize-meal` прямым curl-запросом
(анонимный ключ как Bearer-токен — верификация JWT у Edge Functions
принимает и сам publishable/anon-key, не только сессию пользователя,
приложение вообще не делает логин) — функция ответила за ~1с, то есть
Gemini и ключи живы, бэкенд в целом не сломан.

**Настоящая причина** — прочитал всю цепочку `src/app/add-meal/index.tsx`
→ `analyzing.tsx` → `src/lib/meal-analysis-api.ts` →
`supabase.functions.invoke('recognize-meal', ...)` →
`supabase/functions/recognize-meal/index.ts` →
`supabase/functions/_shared/gemini.ts` (`callGemini`, fetch к Gemini) —
**нигде во всей цепочке не было таймаута**. Ни
`supabase.functions.invoke` на клиенте (у него есть опция `timeout`, но
она не передавалась), ни `fetch` к Gemini в `gemini.ts`, ни `fetch` к
USDA в `usda.ts`. Если сеть на телефоне подвисала (слабый сигнал, большая
base64-картинка с камеры грузится медленно) или сам внешний API просто
не отвечал (не ошибка, а тишина) — промис никогда не резолвился и не
реджектился, `await` в `analyzing.tsx` висел бесконечно. А экран
"Анализ" (`src/app/add-meal/_layout.tsx`, `gestureEnabled: false`,
`headerBackVisible: false`) специально блокирует back-жест и кнопку
назад в хедере, чтобы не прерывать анализ на полпути — то есть
пользователь застревал без единого способа выйти, кроме как убить
приложение целиком.

Это не новый баг от последних правок — судя по старому коммиту
`0d4fd4e` ("Split photo analysis into two calls, show which stage is
running"), зависания были известны и раньше, просто тот коммит добавил
только подпись стадии ("Распознаём блюдо…"/"Считаем калории…"), а не
таймаут.

**Исправлено:**
- `src/lib/meal-analysis-api.ts` — у каждого `supabase.functions.invoke`
  теперь есть `timeout` (60с для `recognize-meal` — там загрузка фото +
  Gemini vision с ретраями до ~37с внутри; 30с для `lookup-nutrients` —
  параллельные запросы к USDA; 50с для `lookup-ingredient` — Gemini
  перевод + USDA последовательно). При таймауте `supabase-js` сам кидает
  `FunctionsFetchError`, он подхватывается уже существующим `.catch()` в
  `analyzing.tsx`, который показывает `Alert` с кнопками
  «Назад»/«Повторить» — то есть сам путь выхода уже был в коде, просто
  никогда не срабатывал, потому что ничего не бросало ошибку.
- `supabase/functions/_shared/gemini.ts` и `_shared/usda.ts` — у
  внутренних `fetch` добавлен `signal: AbortSignal.timeout(...)` (20с
  для Gemini, 10с для USDA на одну попытку), чтобы зависший внешний API
  не вешал саму edge-функцию навечно, а падал с ошибкой, которую уже
  обрабатывает `try/catch` в каждом `index.ts` (возвращает 500 с текстом
  ошибки, что клиент тоже уже умеет показывать).
- Все четыре функции, которые делят эти shared-файлы (`recognize-meal`,
  `lookup-nutrients`, `lookup-ingredient`, `nutrition-advice`),
  передеплоены (`supabase functions deploy <имя>`) и проверены прямым
  curl — отвечают как раньше.
- Клиентская часть (`meal-analysis-api.ts`) закоммичена (`6cc2f31`),
  собрана в APK и подтверждена пользователем.

Урок: любой `await` на сетевой вызов в мобильном приложении (особенно на
нестабильном мобильном интернете) обязан иметь таймаут — без него сбой
сети превращается не в понятную ошибку с кнопкой "Повторить", а в
бесконечное зависание, да ещё и без возможности выйти, если экран
специально блокирует навигацию назад на время операции.

### Клавиатура перекрывала поле ввода ингредиента — потребовалось пять заходов
Заход 1 (коммит `a0e18a7`) скроллил `FlatList` на `requestAnimationFrame`
при фокусе поля — не сработало: один кадр (~16мс) ничтожно мал по
сравнению с длительностью анимации появления клавиатуры.

Заход 2 (коммит `ee489db`) — подписка на
`Keyboard.addListener('keyboardDidShow', ...)`, скролл только когда ОС
подтвердила, что клавиатура реально открылась — тоже не помогло, что
подтвердил пользователь на реальном устройстве уже после того, как этот
фикс попал в собранный APK.

**Настоящая причина ресайза** (нашли на заходе 3): в проекте подключён
`react-native-edge-to-edge` (см. `app.json`) — он рисует окно
edge-to-edge, из-за чего нативный ресайз окна при появлении клавиатуры на
Android (`windowSoftInputMode="adjustResize"`, который экспо ставит по
умолчанию) **не срабатывает**. Экран физически не сжимается, клавиатура
просто накладывается поверх нижней части поверх `FlatList`, который
продолжает думать, что у него полная высота экрана. В документации Expo
(`docs.expo.dev/versions/v57.0.0/config/app/`,
`android.softwareKeyboardLayoutMode`) это прямо описано: включение
translucent-режима статус-бара (то, что фактически делает edge-to-edge)
«may cause unexpected keyboard behavior... you will have to use
`KeyboardAvoidingView`».

Заход 3 (коммит `f95bf12`) — `FlatList` обёрнут в `KeyboardAvoidingView`
(`behavior="height"` на Android, `"padding"` на iOS), она ужимает высоту
через JS вместо нативного ресайза. Пользователь протестировал: список
теперь действительно сжимается и его можно промотать руками, но
**осталась вторая, отдельная проблема** — `scrollToEnd` в подписке на
`keyboardDidShow` скроллил к самому концу `FlatList`, а строка ввода
ингредиента лежала внутри списка *перед* карточкой итогов и кнопкой
сохранения (в `ListFooterComponent`). То есть скролл уезжал мимо поля
ввода к тому, что находится ниже него, а не к самому полю — оно всё ещё
оказывалось за клавиатурой без ручного скролла вверх. Пользователь прямо
попросил: чтобы поле ввода оставалось сразу над клавиатурой, а не «где-то
на промотанном экране».

Заход 4 (коммит `3bba5eb`) — переосмыслили подход: вместо того чтобы
скроллить список к позиции поля, строка ввода
(`newName`/`newGrams`/кнопка «Добавить») вынесена из
`ListFooterComponent` и рендерится отдельным блоком сразу после
`FlatList`, как сосед внутри того же RN-овского `KeyboardAvoidingView` —
по типу закреплённой панели ввода, как в мессенджерах. Идея была верной
(см. заход 5), но конкретная реализация — нет: **пользователь
протестировал и сообщил, что стало хуже**. Панель просто осела к самому
низу экрана, к системной навигационной панели, и клавиатура полностью её
перекрыла — то есть `KeyboardAvoidingView` (`behavior="height"`) на этом
устройстве вообще не реагировал на клавиатуру, не только "докручивал не
туда" (как в заходе 3), а буквально ничего не делал. Встроенный RN
`KeyboardAvoidingView` на Android — известно ненадёжный компонент (много
открытых issue в facebook/react-native именно про Android + edge-to-edge
+ behavior="height"), поэтому третий раз наступать на грабли той же
природы («попробовать ещё один параметр встроенного API») смысла не было.

**Исправлено** (заход 5, коммит после текущего, см. диф) — заменили
источник правды. Вместо построения логики над `Keyboard.addListener`/
`adjustResize`/`KeyboardAvoidingView` (то есть JS-эвристик поверх
ненадёжного на Android слоя) поставили `react-native-keyboard-controller`
(`npx expo install react-native-keyboard-controller`, пир-зависимость
`react-native-reanimated` уже была в проекте). Библиотека держит
клавиатуру через нативные API (`WindowInsetsAnimation` на Android),
а не через события `Keyboard` из RN core. Корень приложения
(`src/app/_layout.tsx`) обёрнут в `<KeyboardProvider>` — без этого
хуки/компоненты библиотеки не работают. Панель ввода ингредиента в
`src/components/meal-editor.tsx` обёрнута в `<KeyboardStickyView
offset={{ closed: 0, opened: 0 }}>` — компонент библиотеки, сделанный
специально под этот сценарий (панель, которая транслируется вверх вместе
с клавиатурой, а не ждёт ресайза контейнера). **Ещё не подтверждено на
реальном устройстве** — это первый прогон этого варианта, и это уже
пятая попытка починить один и тот же баг, так что при следующей неудаче
не пробовать очередной вариант API того же типа — сразу разбираться,
почему нативные инсеты не доходят до JS (возможно, дело не в компоненте,
а в чём-то более глубоком в связке edge-to-edge + new architecture на
этом конкретном устройстве/версии Android).

Уроки:
- Встроенный RN `KeyboardAvoidingView` на Android — не полагаться на
  него вообще, особенно в паре с `react-native-edge-to-edge`. Он либо не
  реагирует на клавиатуру совсем (как в заходе 4), либо ресайзит
  непредсказуемо. Сразу ставить `react-native-keyboard-controller`
  (`KeyboardProvider` в корне + `KeyboardStickyView`/`KeyboardAvoidingView`
  из этой библиотеки) — она работает через нативные инсеты клавиатуры, а
  не через JS-эвристики поверх `Keyboard.addListener`.
- Скролл списка к позиции поля ввода — хрупкое решение, если поле не в
  самом конце списка (`scrollToEnd` найдёт конец списка, а не конец
  видимого поля). Для полей ввода, которые должны быть гарантированно
  видны над клавиатурой независимо от контента вокруг — надёжнее вынести
  их из скроллящегося списка и закрепить отдельной панелью
  (`KeyboardStickyView`), а не пытаться вычислить нужную позицию скролла.
- При работе с клавиатурой на Android не верить собственным глазам в
  симуляторе/на одном фиксе — обязательно ждать подтверждения от
  пользователя на реальном устройстве перед тем, как считать баг
  закрытым: два из пяти заходов (2 и 4) выглядели логично на бумаге, но
  на практике не работали или делали хуже.

### Health Connect — целая сага граблей, если будешь трогать эту часть
1. Конфиг-плагин `react-native-health-connect` регистрирует только
   экран-обоснование разрешений в манифесте — сам
   `<uses-permission android:name="android.permission.health.WRITE_NUTRITION"/>`
   нужно объявлять вручную через `android.permissions` в `app.json` (как
   `RECORD_AUDIO`). Без этого Android вообще не показывает системный
   диалог разрешения.
2. В самой библиотеке (`node_modules/react-native-health-connect`, метод
   `requestPermission` в `HealthConnectManager.kt`) нет `try/catch` вокруг
   нативного вызова — единственный метод в файле без него. Любая нативная
   ошибка там просто проглатывалась вместо того, чтобы отклонить promise.
   Пропатчено через `patch-package`
   (`patches/react-native-health-connect+4.1.3.patch`, см. `postinstall` в
   `package.json`).
3. Финальная причина, почему разрешение выдавалось, но данные не
   записывались: `NutritionRecord` — это `IntervalRecord`, Health Connect
   требует `startTime < endTime` строго. Приём пищи в модели приложения —
   мгновенное событие, поэтому все записи падали с `startTime must be
   before endTime`. Исправлено в `src/lib/health-connect.ts` —
   `endTime = startTime + 1 минута`.
4. Нативный `healthConnectClient` живёт только в рамках текущего процесса
   приложения — после перезапуска приложения он снова не инициализирован,
   даже если разрешение уже выдано и тумблер включён. Исправлено —
   `ensureInitialized()` вызывается перед каждой операцией записи/удаления,
   а не один раз при включении тумблера.
5. `src/lib/health-connect.ts` хранит последнюю ошибку синхронизации в
   AsyncStorage (`getLastSyncError`) и показывает её в Профиле под
   тумблером — полезно для будущей отладки, специально не убирал после
   фикса.
6. Подтверждено на реальном устройстве (Android 16, Samsung).

### Остальное
- USDA FoodData Central API периодически отдаёт 400 без видимой причины —
  в `supabase/functions/_shared/usda.ts` есть ретрай (до 4 попыток).
- Общий фолбэк по нутриентам (`GENERIC_FALLBACK` там же) срабатывает, если
  USDA вообще не находит совпадение — может давать неточные цифры для
  редких продуктов.
- Промпт для Gemini явно разделяет "твёрдая еда" и "напитки/жидкости" —
  раньше "вода, raw" уводила поиск USDA не в ту сторону.
- Фото в истории хранятся как временная cache-ссылка от
  `expo-image-picker` — при очистке кэша Android картинка может перестать
  открываться, данные о калориях не пострадают. Договорились пока не
  чинить.
- Локальный `~/.npm` кэш один раз был испорчен root-owned файлами — если
  `npm install` падает с `EACCES`: `sudo chown -R $(whoami):staff ~/.npm`.
- На macOS для растровых операций с иконками — `sips` (встроен) и Pillow
  (`pip3 install Pillow`).
