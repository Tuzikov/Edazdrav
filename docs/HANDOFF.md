## Текущее состояние — MVP полностью рабочий
- Вкладки Сегодня / История / Профиль, flow добавления блюда
  (фото / галерея / вручную), экран деталей и редактирования уже
  сохранённых приёмов.
- Реальный бэкенд: Supabase Edge Functions (`recognize-meal`,
  `lookup-nutrients`, `lookup-ingredient`, `nutrition-advice` — см. ниже) —
  дёргают Gemini (распознавание фото + перевод названий + рекомендации) и
  USDA FoodData Central (нутриенты). Gemini — платный тир.
- Калькулятор целей (формула Миффлина-Сан Жеора) в Профиле, плюс ручной
  ввод целей.
- **История**: факт/план по калориям и выбранному нутриенту в шапке
  каждого дня; счётчик «N дней в режиме 👍»; **сводка за произвольный
  период** — свой календарь (`src/components/period-calendar.tsx`, без
  внешних зависимостей, тап-тап выбор диапазона) показывает итог и среднее
  в день по калориям+БЖУК против плана; кнопка «Получить рекомендации»
  отправляет эту сводку в новую Edge Function `nutrition-advice`, которая
  просит у Gemini текстовые советы по рациону/активности — **только по
  нажатию кнопки**, не автоматически.
- **MealEditor** (общий компонент для нового блюда и редактирования уже
  сохранённого): у каждого ингредиента теперь подписаны калории (`≈N ккал`,

## На заметку (грабли, на которые уже наступали)

### Supabase keep-alive — паузился повторно, пинг был слишком редким
Несмотря на воркфлоу `.github/workflows/keep-alive.yml` (добавлен ещё в
августе), проект **снова ушёл в паузу** в сентябре. История запусков
показала: пинг `2026-09-14` получил живой ответ `200` от базы, а
следующий по расписанию (`2026-09-17`, через 3 дня) упал с
`curl: (6) Could not resolve host` — проект был уже полностью выгружен, то
есть заметно раньше формального 7-дневного порога бездействия. Расписание
было `пн и чт` (2 раза в неделю) — судя по всему, недостаточно часто:
документация Supabase формулирует порог расплывчато («обычно достаточно
нескольких запросов к БД **в день** на протяжении недели»), то есть их
реальная эвристика активности жёстче буквальных «7 дней» без запросов.
**Исправлено**: расписание пинга увеличено до раза в 6 часов (`0 */6 * *
*`). Если и это не поможет — единственный по-настоящему надёжный вариант
это платный тариф Supabase (Pro, там паузы по неактивности нет вообще);
пинг любой частоты — это обход, а не гарантия.

**Важно**: разбудить уже приостановленный проект **нельзя** ни через
`supabase` CLI (проверено — там только `list/create/api-keys/delete`, ни
`restore`, ни `resume` нет), ни через какой-либо API — только кнопка
«Restore project»/«Resume» в Supabase Dashboard
(https://supabase.com/dashboard/project/iwqabjqsrqvmqciikzqn), и нажать
её может только сам пользователь (залогиненный человек), не агент.

### Клавиатура перекрывала поле ввода ингредиента — потребовалось три захода
Первая попытка (коммит `a0e18a7`) скроллила `FlatList` на
`requestAnimationFrame` при фокусе поля — не сработало: один кадр (~16мс)
ничтожно мал по сравнению с длительностью анимации появления клавиатуры.
Вторая попытка (коммит `ee489db`) — подписка на
`Keyboard.addListener('keyboardDidShow', ...)`, скролл только когда ОС
подтвердила, что клавиатура реально открылась — тоже не помогло, что
подтвердил пользователь на реальном устройстве уже после того, как этот
фикс попал в собранный APK.

**Настоящая причина** (нашли только на третьем заходе): в проекте
подключён `react-native-edge-to-edge` (см. `app.json`) — он рисует окно
edge-to-edge, из-за чего нативный ресайз окна при появлении клавиатуры на
Android (`windowSoftInputMode="adjustResize"`, который экспо ставит по
умолчанию) **не срабатывает**. Экран физически не сжимается, клавиатура
просто накладывается поверх нижней части поверх `FlatList`, который
продолжает думать, что у него полная высота экрана — поэтому скроллить
было физически некуда, к какому бы событию ни привязываться. В документации
Expo (`docs.expo.dev/versions/v57.0.0/config/app/`,
`android.softwareKeyboardLayoutMode`) это прямо описано: включение
translucent-режима статус-бара (то, что фактически делает edge-to-edge)
«may cause unexpected keyboard behavior... you will have to use
`KeyboardAvoidingView`».

**Исправлено** (коммит после `8ec950d`): `FlatList` в
`src/components/meal-editor.tsx` обёрнут в `KeyboardAvoidingView`
(`behavior="height"` на Android, `"padding"` на iOS) — она ужимает высоту
обёрнутого view через JS по событиям клавиатуры, не полагаясь на нативный
`windowSoftInputMode`. Подписка на `keyboardDidShow` со скроллом оставлена
поверх — теперь она докручивает уже внутри реально уменьшенной области.
**Ещё не подтверждено на реальном устройстве** — это первый прогон этого
конкретного фикса.

Урок: если в проекте есть `react-native-edge-to-edge` (или Android
15+ enforced edge-to-edge), не полагаться на `adjustResize` вообще ни для
чего, связанного с клавиатурой — сразу закладывать `KeyboardAvoidingView`
(или `react-native-keyboard-controller`, если `KeyboardAvoidingView`
окажется недостаточно надёжным на Android в более сложных случаях).

### Health Connect — целая сага граблей, если будешь трогать эту часть
1. Конфиг-плагин `react-native-health-connect` регистрирует только
   экран-обоснование разрешений в манифесте — сам
   `<uses-permission android:name="android.permission.health.WRITE_NUTRITION"/>`
   нужно объявлять вручную через `android.permissions` в `app.json` (как
   `RECORD_AUDIO`). Без этого Android вообще не показывает системный
   диалог разрешения.
2. В самой библиотеке (`node_modules/react-native-health-connect`, метод
   `requestPermission` в `HealthConnectManager.kt`) нет `try/catch` вокруг
   нативного вызова — единственный метод в файле без него. Любая нативная
   ошибка там просто проглатывалась вместо того, чтобы отклонить promise.
   Пропатчено через `patch-package`
   (`patches/react-native-health-connect+4.1.3.patch`, см. `postinstall` в
   `package.json`).
3. Финальная причина, почему разрешение выдавалось, но данные не
   записывались: `NutritionRecord` — это `IntervalRecord`, Health Connect
   требует `startTime < endTime` строго. Приём пищи в модели приложения —
   мгновенное событие, поэтому все записи падали с `startTime must be
   before endTime`. Исправлено в `src/lib/health-connect.ts` —
   `endTime = startTime + 1 минута`.
4. Нативный `healthConnectClient` живёт только в рамках текущего процесса
   приложения — после перезапуска приложения он снова не инициализирован,
   даже если разрешение уже выдано и тумблер включён. Исправлено —
   `ensureInitialized()` вызывается перед каждой операцией записи/удаления,
   а не один раз при включении тумблера.
5. `src/lib/health-connect.ts` хранит последнюю ошибку синхронизации в
   AsyncStorage (`getLastSyncError`) и показывает её в Профиле под
   тумблером — полезно для будущей отладки, специально не убирал после
   фикса.
6. Подтверждено на реальном устройстве (Android 16, Samsung).
